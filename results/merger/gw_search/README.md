`grteclyn_wrapper.gw_search.cli` — see that package's README for the method
and for what each number is allowed to mean.

Run all four from the repository root, after

```bash
export PYTHONPATH=$PWD/grteclyn-wrapper/src
alias gws="grteclyn-wrapper/.venv/bin/python -m grteclyn_wrapper.gw_search.cli"
```

**What changed on 2026-10-05** (GPU_PLAN, same date): injections sit midway
between two rungs, so they test the bank's spacing; the same-window fitting
factor is the bank's maximum; the horizon takes σ from every template; the
two blocks' 64 s overlap is counted once and its duplicate triggers dropped;
and time slides wrap on the analysed time, so every slide carries the whole
livetime. A recovery above 100 % of optimal (the 85 M⊙ plunge, 123 %) is a
heavier rung, filtered from a lower corner, collecting the injected strain
below the plunge record's own 130 Hz corner.

**Livetime is limited by the network and by segment geometry, not by the
method.** Two blocks, not six: a 4096 s block needs 4096 s of *contiguous*
coincident CBC\_CAT3 time, and this window holds two such stretches. Widen
`--gps-start/--gps-end` to get more; the strain cache makes the run
resumable, so nothing already downloaded is fetched again.

**Fetch in file-sized blocks.** gwpy downloads the whole enclosing 4096 s
GWOSC file (~130 MB) however little is asked for, so eight 512 s blocks
inside one file cost eight full transfers of it. `--block-s 4096` turns that
into one.

**The proxy is bypassed, deliberately.** This host exports
`http(s)_proxy=http://127.0.0.1:8119`; `GwoscStrainSource` clears it on
construction so fetches take the cluster's own route. Measured on the same
4 MB range request on 2026-09-18: **884 kB/s via the proxy, 1580 kB/s
direct**. The reliability matters more than the speed — that proxy is one
local process, and when it exited mid-scan every in-flight fetch died with
`ProxyError(ConnectionRefused)`, which in the log is indistinguishable from
an unreachable archive. Set `GW_SEARCH_USE_PROXY=1` on a host where the
proxy is the only way out. With it bypassed, four 134 MB block-detectors
land in about 9 min.

## Two things about the scan that are easy to get wrong

**Block length is a network decision, not a physics one.** GWOSC serves
4096 s files and gwpy downloads the whole enclosing file however little is
asked for, so a 512 s block costs exactly the same transfer as a 4096 s one
and buys an eighth of the livetime. On a slow link, `--block-s 4096`.

**Livetime is the limit on what may be claimed, and it is stated in the
output.** The smallest false-alarm rate a search can report is one per its
own background livetime — `background.floor_far_per_year` in the JSON. A
foreground event louder than every time slide has not been shown to be
significant beyond that floor, which is why the rate is counted as
`(N_louder + 1) / T_background` and not `N_louder / T_background`.

## Strain cache

Downloaded data lives in `runs/gw_search/strain_cache/` (git-ignored,
override with `GW_SEARCH_CACHE`), keyed by `(ifo, gps_start, gps_end, rate)`,
plus the cached science-segment query as JSON. Re-deriving any number here —
a different ranking statistic, more time slides — touches the network zero
times.
