# checkpoint_interval counts COARSE (level-0) STEPS, not code units, and it is
# never re-derived automatically when the grid changes.  The arithmetic:
#
#     dt_coarse   = dt_multiplier * L / N1  = 0.1 * 64 / 64 = 0.1
#     total steps = stop_time / dt_coarse   = 80 / 0.1      = 800
#
# so the 2000 this file used to carry NEVER FIRED -- the run would have
# produced exactly one checkpoint, written at stop_time by the end-of-run
# branch in Main_BinaryWormhole.cpp, and a crash at t = 70 would have left
# nothing to restart from.  100 steps = 10 code units gives 8 checkpoints
# across the run, i.e. at most ~10 units of lost work.
#
# Re-derive this if dt_multiplier, L, N1 or stop_time change.  Aim for roughly
# one checkpoint per hour of wall time; the Stage 2 grid managed ~19 code
# units/hour, but this grid is coarser at level 0 and deeper (max_level 5), so
# time the first hour of a real run and adjust.
#
# Cost: a checkpoint holds all 27 evolved variables on every level, against
# the 7 a plotfile holds here, so expect a few GB each.  AMReX does NOT prune
# old checkpoints -- they accumulate on scratch until deleted by hand.
#
# To resume, add a line pointing at the checkpoint directory:
#     amr.restart = /tmp/grteclyn_scratch/<run>/BinaryWormholeChk00300
#
# It must be amr.restart -- that is the key AMReX itself reads (AMReX_Amr.cpp,
# Amr::InitAmr) and the only one BaseParameterChecker validates.  There is a
# root-level `restart_file` key in AMReXParameters.hpp; do NOT use it.  Its
# presence flips restart_from_checkpoint on, but the string behind it is never
# read from the params file, so the existence check then runs against an empty
# path and the run aborts with a parameter error instead of restarting.
